## 一、原型设计（40%）

我们使用**高保真可交互原型**呈现设计，覆盖前台用户端 8 个页面与后台管理端 4 个页面，全部可点击、带真实感数据与状态反馈。原型围绕学生点餐的真实动线展开：先解决"今天吃什么"的决策问题，再解决"怎么点更划算"的性价比问题，最后落到加购下单的完整闭环。

### 1.1 信息架构：12 个页面

原型采用底部 TabBar（用户端）+ 侧边导航（管理端）的经典布局，前台/后台一键切换：

```text
校园美食点餐平台
├── 前台应用（用户端）
│   ├── P1 登录/注册（学号+密码，注册含姓名与校区）
│   ├── P2 首页（商家分类入口 + 推荐位 + 快捷入口）
│   ├── P3 商家列表与详情（食堂/商铺/小摊筛选 + 公告 + 菜品）
│   ├── P4 菜品详情（本店价/原价/参考价 + 省钱标签 + 规格）
│   ├── P5 AI 选餐对话（口味/预算/辣度 → 推荐卡片 + 来源标注）
│   ├── P6 美食榜单（热销/好评/低价/划算四类）
│   ├── P7 购物车与结算（数量修改 + 地址 + 生成订单）
│   └── P8 个人中心（资料 + 我的订单 + 地址 + 评价入口）
└── 后台管理（管理端）
    ├── P9  管理首页（用户/商家/订单/评价统计看板）
    ├── P10 商家与菜品管理（上下架 + 价格与参考价维护）
    ├── P11 订单与评价管理（状态流转 + 评价审核）
    └── P12 智能体配置（模型平台切换 + 兜底规则开关）
```

### 1.2 前台应用原型（用户端）

**P2 首页**是学生的入口：顶部按食堂窗口、周边商铺、路边小摊三类场景切分，中部是 AI 选餐与划算榜的推荐位，下方以九宫格快捷入口把学生直接导向分类浏览、比价、榜单与下单四大核心功能。

**P4 菜品详情**体现我们的第一个亮点——**跨平台比价可视化**。一张卡片上同时呈现本店售价、划线原价与其他平台参考价，系统自动计算差价并以醒目的"省 ¥N"标签呈现；当当前价低于参考价时才显示省钱标签，价差即为划算榜的排序依据。这让"性价比"从一句口号变成看得见、可比对的 UI 信息。

**P5 AI 选餐对话**是第二个亮点。用户说出"辣一点、20 元以内"这类诉求，对话页返回智能体的推荐话术与最多 3 道菜品卡片，每张卡片都可直接加购或进店。最关键的是**来源标注**：卡片明确区分"大模型推荐""大模型文字+本地菜品""本地规则推荐"三种来源，让用户知道结果从哪来、可不可信。

**P6 美食榜单**提供热销、好评、低价、划算四类排行，同学可按自己最在意的维度切换参考；其中划算榜严格按省钱幅度从高到低取前 10 道菜品。

**P7 购物车与结算**串起点餐闭环：加购、改数量、选地址、填写备注，结算后生成示例订单，订单详情可查看明细、总价与状态，并支持取消。

### 1.3 后台管理原型（管理端）

后台做了 4 个页面：P9 管理首页给出总用户/商家/订单/评价统计与近 7 日趋势；P10 商家与菜品管理支持上下架及价格、参考价维护（比价数据在此维护，保证前台省钱标签有数据源）；P11 订单与评价管理支持订单状态流转与评价审核；P12 智能体配置可切换大模型平台（火山方舟等）、调整兜底规则开关与推荐条数。

### 1.4 原型的交互与规则说明

原型不是静态图片，而是一套带规则的交互系统。我们把设计规则显式写进原型与搭建对照表：

| 编号 | 触发 | 规则 / 反馈 | 对应需求 |
| --- | --- | --- | --- |
| R1 | 输入口味/预算/辣度诉求 | AI 返回推荐话术 + 最多 3 道菜品卡片 | FR-2.2 |
| R2 | 大模型请求失败/超时/解析异常 | 自动回退本地关键词规则，并标注来源为本地兜底 | FR-2.3 |
| R3 | 当前价低于参考价 | 菜品卡显示"省 ¥N"省钱标签，差额=参考价−当前价 | FR-5.2 |
| R4 | 点击加购 | 购物车数量与角标实时更新 | FR-8.1 |
| R5 | 切换到划算榜 | 按省钱幅度降序展示，取前 10 道 | FR-5.3 / FR-6.2 |
| R6 | 提交评价 | 本机缓存保存并立即出现在对应评价列表 | FR-7.2 |
| R7 | 点击结算 | 生成示例订单，含明细、总价、地址与备注 | FR-8.2 |
| R8 | 未登录访问下单/评价 | 引导跳转登录/注册页 | FR-1 |

### 1.5 本组原型的突出特点

**特点一：比价可视化。** 参考价、原价、本店价三层价格信息并列呈现，差价用"省 ¥N"直接标在菜品卡上，性价比一眼可辨——"划算"从主观感受变成可计算、可排序的数据。

**特点二：AI 选餐双链路兜底。** 大模型链路与本地规则链路并存，接口失败、超时或解析异常时自动回退，卡片明确标注来源。这样既保留了大模型的灵活推荐，又保证演示过程中对话不空白、结果都来自本地已有菜品库。

**特点三：一体化点餐闭环。** 从浏览、决策（AI 选餐）、比价、榜单、评价到加购下单，全部收敛在一个小程序里，学生不需要在多个应用间跳转，这是竞品分散式体验难以提供的一站式价值。

## 二、概要设计（40%）

我们按"自顶向下、分层描述"的原则做概要设计：先用思维导图展示功能全景，再用分层架构图定框架，最后用用例图、活动图、类图、时序图、协作图分别从需求、流程、结构、算法、协作五个视角刻画系统。所有图采用一致的图形符号与配色，图号在本文档与两份说明书中统一。

### 2.1 功能思维导图

*图 1　功能思维导图：8 个一级模块 F1–F8，逐级展开子功能。模块编号在需求、设计、原型、博客中全程统一。（配图：assets/food_mindmap.png）*

八个一级模块分别是：F1 登录注册与个人中心、F2 AI 智能选餐、F3 商家与菜品浏览、F4 分类与搜索、F5 比价与性价比、F6 美食榜单、F7 用户评价、F8 购物车与下单（含收货地址）。

### 2.2 系统分层架构

*图 2　系统分层架构图：表现层 → 接口适配层 → 能力层 → 数据层四层，右侧为外部依赖（火山方舟大模型）。*

系统分四层，职责单一、边界清晰：

| 层次 | 关键组件 | 职责 |
| --- | --- | --- |
| 表现层 | 微信小程序原生页面（P1–P12，WXML/WXSS/JS） | 页面渲染、输入校验、对话展示、卡片翻转与价格标签呈现 |
| 接口适配层 | utils/api.js（Promise 化请求适配） | 统一数据访问入口，屏蔽本地 Mock 与真实后端差异，返回模拟 JSON 报文 |
| 能力层 | AIAgent 智能体、比价/榜单计算、本地规则兜底 | 构造提示词、解析大模型返回、按本地菜品库匹配、计算省钱幅度与榜单排序 |
| 数据层 | 本地 Mock（菜品/商家/订单/评价）+ 本地缓存 | 提供演示数据，保存本机新增评价、购物车与登录态 |

这样的分层带来两个好处：一是**大模型可替换**——通过适配层切换平台而不改页面代码；二是**后端可平滑接管**——后续接真实后端时只需替换接口适配层的实现，页面无需改动。

用户用例覆盖点餐主流程：登录注册、浏览商家菜品、AI 选餐、查看比价与榜单、提交评价、加购下单、维护地址。管理员用例覆盖系统运维：用户与内容管理、商家菜品上下架、订单与评价管理、智能体配置。其中"AI 选餐"包含"调用大模型"，而"本地规则兜底"是它的扩展行为——这些关系把双链路兜底写进了需求模型。

### 2.4 系统类图（结构视角）

*图 4　系统类图：9 个核心类，标注属性、方法与类间关系。（配图：assets/food_class.png）*

系统按职责划分 9 个核心类：**User**（用户）、**Restaurant**（商家）、**Dish**（菜品）、**Category**（分类）、**Order**（订单）、**OrderItem**（订单明细）、**Review**（评价）、**Address**（收货地址）、**AIAgent**（智能体，含 recommend() / localRecommend() / callArk() 方法）。

*图 5　业务活动图：用户 / 前端 / 适配层 / 大模型 / 数据层五泳道，含 AI 选餐与下单两条主支路及两条异常分支。（需补图）*

### 2.8 数据库设计

数据库采用 ER 模型建模，共 9 个实体，均满足第三范式。

*图 8　系统实体关系图（ER 图）：9 个实体，PK/FK 标注，1:N 基数。（需补图）*

**关系数据模型**（PK 主键，FK 外键）：

```text
User(user_id, student_id, name, avatar, campus, role)
Restaurant(id, name, type, rating, monthly_sales, delivery_time, delivery_fee,
           min_order, avg_price, review_count, tags, notice, is_open)
Dish(id, name, price, original_price, compare_price, image, description,
     category_id FK, restaurant_id FK, sales, stock, review_count, tags, spec, spicy)
Category(id, name, icon, count)
Review(id, target_type, target_id, user_id FK, user_name, rating, content, time, likes)
Address(id, user_id FK, name, phone, campus, building, room, detail, is_default)
Order(id, user_id FK, items_json, total_price, status, create_time,
      restaurant_name, address, remark)
OrderItem(dish_id FK, order_id FK, name, price, quantity, image)
AIAgentConfig(id, enabled, platform, api_url, model, max_recommend, fallback_enabled)
```

**对象关系映射（ORM）** 的一个关键设计是**比价字段同源**：`Dish.price`、`Dish.original_price`、`Dish.compare_price` 三个字段共同支撑省钱标签与划算榜——"省 ¥N"= compare_price − price，划算榜按该差值排序，保证 UI 展示与排序口径一致。另一个关键是**订单明细的聚合映射**：`Order.items_json` 在展示层解析为多个 `OrderItem` 对象，写回时序列化存储，既保留关系模型的清晰，又适配本地 Mock 的存储形态。

详细的表结构、字段类型、索引、数据字典与安全一致性设计，见《码上同行_数据库设计说明书》。

## 三、后端设计展示

本期为课程原型，后端以"本地数据层 + 接口适配层"的形态呈现，核心设计思想是**一切数据访问经过适配层、一切大模型调用经过智能体封装**。这里补充三处后端设计要点：

**① 接口契约设计。** `utils/api.js` 把每个数据访问方法 Promise 化，返回结构统一的模拟 JSON 报文。这样页面层只面向稳定契约编程，后续接真实 HTTPS 后端时，改动集中在适配层内部，不动页面。

```javascript
// 适配层方法示意：返回 Promise，页面无需关心数据来自 Mock 还是远端
function getDishList(params) {
  return Promise.resolve({ code: 0, data: mockDishes.filter(/* ... */) });
}
```

**② 大模型调用的兜底包装。** 前端经 `wx.request` 以 OpenAI 兼容格式调用火山方舟 `chat/completions`：请求头带 Authorization，请求体含 model 与 messages；响应从 `choices[0].message.content` 取文本，解析其中的话术与菜品编号再映射本地菜品。一旦请求失败、超时或解析异常，立即回退本地关键词规则，保证对话不空白。

**③ 二段式结果与来源标注。** 大模型返回的菜品编号先映射成本地菜品对象，再连同来源标记一起交给页面；页面据来源标记渲染"大模型推荐/本地兜底"角标，既保证结果可控，又让推荐过程可解释。

### 4.3 协作过程记录

本次设计阶段我们沿用了第一次作业形成的协作方式：

1. **契约先定，再各自动手。** 作业发布当天，三人线上对齐：模块编号 F1–F8、实体命名、图号、验收标准 A1–A8 全部锁死，写入《设计基线》，任何人不得自行改名——这保证了后面 8 张图、2 份文档、12 页原型里"同一个东西叫同一个名字"。
2. **分工并行，接口解耦。** 前端（林鸿永）与后端（曾堉源）各做各的，中间靠统一的接口适配层契约衔接；队长（唐嘉璇）从 A1–A8 反向核对设计覆盖，发现"本地规则兜底"在活动图里没画，回推动图补上分支。
3. **工具与平台。** 使用腾讯文档协作撰写设计基线、GitHub Issues 跟踪待办与缺陷、腾讯会议做两轮设计评审（原型草图评审、定稿评审）。三位成员均在团队仓库有提交记录https://github.com/ZYY190/food/commits/main（提交记录）。

## 六、总结：我们在设计阶段学到什么

这次作业让我们真正体会到，设计不只是把图画出好看，更是提前把分歧点摆到台面上。做 ER 图时，为了省钱幅度到底存在哪个字段、售价与参考价如何对应，我们翻出了第一次作业的问卷与需求原文，最后统一成 `compare_price − price` 的口径，让省钱标签与划算榜排序天然一致——"比价"在数据结构上自洽了，UI 才不会自相矛盾。

另一个收获是接口的向后兼容。本地 Mock 与接口适配层的设计，让我们意识到"能跑的演示代码是一种资产"：页面只认 Promise 契约，后续把 Mock 换成真实后端、把前端直连换成后端中转，都不必推倒重来。设计文档不是写给老师看的，是写给几周后写代码的自己看的——写得越准、图越清楚，后面越不用猜。
