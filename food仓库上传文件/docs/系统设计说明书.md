# 引言

## 编写目的

本文档在《校园美食点餐平台软件需求分析说明书》的基础上，描述系统的总体设计、体系架构、功能模块、UML 模型、接口与数据结构，作为后续详细设计、编码实现与测试验收的依据。本文档面向课程教师、助教、评审同学及团队内部成员，力求设计决策可追溯、模块边界清晰、图文一致。

## 背景

在校学生日常点餐面临“不知道吃什么”和“同款菜不知道哪里更划算”两个真实困扰，校园餐饮供给又分散在食堂窗口、周边商铺和路边小摊三类渠道。项目以微信小程序为载体，整合三类商家，用大模型智能对话解决选择困难，用跨平台比价与榜单呈现性价比，并打通从浏览到下单的完整链路。本说明书对应第二次团队作业的设计阶段产出。

# 总体设计

## 需求规定

系统面向在校学生与教职工，核心需求为：登录注册与个人中心、商家与菜品浏览、分类与搜索、AI 智能选餐、跨平台比价、美食榜单、用户评价、购物车与下单及收货地址维护。非功能需求包括性能（浏览与检索 2 秒内响应、AI 首条结果 5 秒内返回）、可用性、安全与隐私（演示密钥不进正式包、不采集无关敏感信息）、可维护性与多端兼容性。详细需求见需求分析说明书。

## 运行环境

| 项 | 要求 |
| --- | --- |
| 客户端 | 微信客户端（iOS / Android），微信开发者工具用于开发与调试 |
| 前端技术 | 微信小程序原生 WXML + WXSS + JavaScript |
| 大模型服务 | 火山方舟，OpenAI 兼容 chat/completions 接口 |
| 数据存储 | 课程原型阶段为本地 Mock + 本地缓存；正式上线预留后端数据库 |
| 网络 | 演示阶段前端经 wx.request 直连大模型；正式上线由后端中转 |

## 基本设计概念与处理流程

设计遵循三条主线：其一，“分层解耦”——页面只依赖适配层契约，数据来自 Mock 还是远端对页面透明；其二，“双链路兜底”——AI 选餐同时保留大模型链路与本地规则链路，保证演示不空白且结果可控；其三，“数据同源”——比价字段（本店价、原价、参考价）统一支撑省钱标签与划算榜，避免展示与排序口径不一致。

典型处理流程：学生浏览商家菜品→在对话页输入口味/预算诉求→智能体经适配层调用方舟、解析返回并匹配本地菜品→生成带来源标注的推荐卡片→加购→选择地址结算→生成订单并写入本地 Mock。

## 系统结构

系统按四层组织，自顶向下为表现层、接口适配层、能力层与数据层，右侧为外部依赖（火山方舟大模型）。各层职责单一、边界清晰，如图 2 所示。

图 2　系统分层架构图

| 层次 | 关键组件 | 职责 |
| --- | --- | --- |
| 表现层 | 小程序页面 P1–P12（WXML/WXSS/JS） | 页面渲染、输入校验、对话展示、卡片与价格标签呈现 |

## 人工处理过程

课程原型阶段无人工后台处理环节；商家资料、菜品价格与参考价由团队整理录入 Mock 数据。正式上线后，商家入驻审核与评价审核可由管理员在后台人工处理。

## 尚未解决的问题

（1）真实商家与跨平台价格的自动采集与同步机制；（2）订单、评价、地址的后端持久化与用户隔离；（3）大模型接口由前端直连改为后端中转后的密钥管理与配额控制；（4）评价与收藏的完整业务规则。上述事项列入后续迭代，不影响本期设计阶段目标。

# 接口设计

## 用户接口

用户接口为小程序页面，采用底部 TabBar（用户端）与侧边导航（管理端）布局，配色统一（主色蓝 #2F5496、强调橙 #FF6B35）。输入以文本框、选择器、按钮为主，反馈以 Toast、角标、状态标签呈现。登录/注册页含表单校验，对话页区分用户气泡与智能体气泡并附来源角标，菜品卡并列展示三层价格与省钱标签。

## 外部接口

系统与外部大模型通过 OpenAI 兼容接口交互：POST 请求至方舟 chat/completions，请求头携带 Authorization: Bearer <key>，请求体含 model 与 messages；响应从 choices[0].message.content 取回复文本，解析话术与菜品编号后映射本地菜品。演示密钥仅用于原型，正式上线由后端中转。

## 内部接口

内部接口即适配层契约，方法返回 Promise、模拟 JSON 报文（含 code 与 data）。页面仅调用适配层方法，不直接访问 Mock 或大模型；后续接真实后端时仅在适配层内将本地调用替换为 HTTPS 请求，页面代码不变。主要方法包括：getRestaurantList、getDishList、searchDish、getRanking、submitReview、addToCart、createOrder、aiRecommend 等。

# 系统数据结构设计

## 逻辑结构设计要点

系统采用关系模型，共 9 个实体（User、Restaurant、Dish、Category、Order、OrderItem、Review、Address、AIAgentConfig），均满足第三范式。核心为“用户—订单—明细”下单链与“商家—菜品—分类”供给链。ER 图见图 8，详细表结构见《数据库设计说明书》。

![图](assets/er.svg)

图 8　系统实体关系图（ER 图）

## 物理结构设计要点

课程原型阶段数据以本地 Mock（JavaScript 对象数组）与本地缓存形式存放，按实体分集合组织；主键采用字符串或自增 ID，外键以 ID 引用。正式上线后迁移至关系数据库，为高频查询字段（菜品分类、商家类型、订单用户、评价目标）建立索引。

## 数据结构与程序的关系

表现层通过适配层读取实体数据并以视图模型渲染；Order.items_json 在展示层解析为多个 OrderItem 对象，写回时序列化存储；比价与榜单模块直接读取 Dish 的三价字段计算省钱幅度；AIAgent 按菜品编号从本地菜品库匹配对象。

# 运行设计

## 运行模块组合

基本浏览链路由表现层 + 适配层 + 数据层组成；AI 选餐链路在此基础上加入能力层并外部连接方舟大模型；下单链路由表现层 + 适配层 + 数据层组合完成写入。各组合按需加载，模块间仅经适配层契约交互。

## 运行控制

运行由用户操作驱动：页面事件触发适配层调用，适配层返回 Promise，页面依据 code 渲染结果或错误提示。大模型调用为异步，失败或超时由兜底逻辑接管，保证对话链路持续可用。

## 运行时间

浏览与检索目标 2 秒内响应；AI 选餐首条结果目标 5 秒内返回；本地 Mock 操作近似即时。大模型网络延迟为主要不确定项，通过兜底机制保障体验下限。

# 系统出错处理设计

## 出错信息

| 错误场景 | 出错信息 / 反馈 |
| --- | --- |
| 大模型请求失败/超时/解析异常 | 回退本地规则推荐，卡片标注“本地兜底”来源 |
| 搜索无结果 | 提示“未找到相关菜品” |
| 未登录下单/评价 | Toast 提示并跳转登录/注册页 |
| 购物车为空结算 | Toast 提示“购物车为空” |
| 表单校验不通过 | 对应输入框下方显示红色提示 |

## 补救措施

大模型异常由本地规则兜底接管，保证推荐不空白；数据读取异常由适配层返回错误码，页面展示友好提示并允许重试；关键写操作（下单、评价）在本地缓存保存，避免刷新丢失。

## 系统维护设计

系统采用分层与模块化设计，页面、适配层、Mock 数据分离，便于定位与替换；大模型平台通过适配层可切换；命名与编号规范统一（F1–F8、A1–A8），降低维护成本。正式上线后将补充日志与监控。
